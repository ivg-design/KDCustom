# Rive panel-aware dial routing: feasibility and diagnostic plan

## Verdict

Automatic active-panel detection is **not established** for the installed Rive desktop editor. The proven case is narrower: a focused numeric `AXTextArea` exposed readable text, and the physical outer dial adjusted and retained values after Enter in both directions at 0.01 normally, 0.001 with Option, and 0.1 with Shift. That confirms numeric editing in that field, not that the timeline, hierarchy, and canvas expose stable panel identity. A previous AX inspection saw only an `AXGroup`; a later accessibility client saw richer semantics. Which client action caused the change, whether it persists, and whether it exposes panel boundaries remain untested.

The recommended path is to keep the classifier inside Keydial Studio, first probe Rive's AX tree across panels without modifying a document, then add pointer-aware classification only for panels whose focus metadata is absent or ambiguous. A separate daemon has no special access to Rive's internal state: it would use the same AX and event APIs, add another privacy/trust boundary and IPC, and complicate cancellation. The app already has an AX worker, foreground gating, physical-input observation, and ordered dial-only rules ([FocusedInputObserver.swift](../Native/Platform/FocusedInputObserver.swift), [StudioModel.swift](../Native/App/StudioModel.swift), [Models.swift](../Native/Core/Models.swift)). A helper is warranted only if later measurement shows isolation is needed for blocking AX/OCR work or the app's lifecycle cannot meet a real requirement.

## What each signal actually means

| Signal | Can answer | Cannot safely answer alone |
| --- | --- | --- |
| `AXFocusedUIElement` plus parent chain | Where keyboard focus is reported; possibly a labeled panel ancestor | Last panel clicked when keyboard focus stays in a text field; unlabeled custom canvas surface |
| AX hit test at a click point | The accessibility object under that point, respecting window layering | Keyboard focus after the click; panel identity if only a generic root is returned |
| Observed mouse-down/up in Rive | The most recent physical pointer interaction and its coordinates | Whether the click changed Rive's keyboard target, especially during drags or transient overlays |
| Calibrated window-relative region | Approximate panel of a click when AX is generic | Panel identity after resizing, docking, mode switches, popovers, display changes, or a layout update unless recalibrated |
| Rive editor API, if one exposes active surface | Potentially authoritative editor state | Availability cannot be inferred from the MCP feature list or file/runtime scripting |
| Vision/OCR | Visible labels and rough layout when AX is insufficient | Keyboard focus or action ownership; it also requires capture permission and adds latency/fragility |

Apple documents `AXFocusedUIElement`, `AXParent`, window, position, and size attributes for traversing and locating accessible controls ([attributes](https://developer.apple.com/documentation/applicationservices/carbon_accessibility/attributes), [parent](https://developer.apple.com/documentation/applicationservices/kaxparentattribute), [window](https://developer.apple.com/documentation/applicationservices/kaxwindowattribute)). `AXUIElementCopyElementAtPosition` hit-tests a screen point and can fail or return no element; the result follows window z-order ([Apple](https://developer.apple.com/documentation/applicationservices/1462077-axuielementcopyelementatposition)). An AX observer can register on the application to receive focus-change notifications, but a notification exists only when the target sends it ([Apple](https://developer.apple.com/documentation/applicationservices/axnotificationconstants_h)). A global `NSEvent` monitor receives copies of other apps' mouse events asynchronously and cannot alter them ([Apple](https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents%28matching%3Ahandler%3A%29)). These are supported observation mechanisms, not evidence that Rive emits semantic panel IDs.

Flutter distinguishes keyboard focus from pointer interaction: clicking *may* request a new focus, while focus persists until moved ([Flutter focus guide](https://docs.flutter.dev/ui/interactivity/focus)). Flutter's standard widgets can populate accessibility semantics, but custom widgets need appropriate semantics ([Flutter accessibility guide](https://docs.flutter.dev/ui/accessibility/assistive-technologies)). Rive's documentation about **Semantics** describes accessibility authored into a Rive animation and its runtime mapping, not the desktop editor's own panel accessibility contract ([Rive semantics](https://rive.app/docs/editor/accessibility/semantics)).

In current upstream Flutter macOS source, `FlutterView` itself advertises an accessible `AXGroup` labeled with the app name ([FlutterView.mm, lines 154-173](https://github.com/flutter/flutter/blob/5048996dd0d3868fe53616c704c94d97a497acbb/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterView.mm#L154-L173)). The engine [initializes semantics disabled](https://github.com/flutter/flutter/blob/5048996dd0d3868fe53616c704c94d97a497acbb/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterEngine.mm#L530-L548), listens for `NSApplicationDidChangeAccessibilityEnhancedUserInterfaceNotification` (commented as a private VoiceOver status notification), and uses its `AXEnhancedUserInterface` user-info value to set semantics enabled ([FlutterEngine.mm, lines 62-65](https://github.com/flutter/flutter/blob/5048996dd0d3868fe53616c704c94d97a497acbb/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterEngine.mm#L62-L65), [lines 1402-1418](https://github.com/flutter/flutter/blob/5048996dd0d3868fe53616c704c94d97a497acbb/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterEngine.mm#L1402-L1418), [lines 1547-1555](https://github.com/flutter/flutter/blob/5048996dd0d3868fe53616c704c94d97a497acbb/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterEngine.mm#L1547-L1555)). Enabling creates each view controller's accessibility bridge and asks the embedder for semantics; subsequent semantics updates attach the native root as the Flutter view's child ([FlutterEngine.mm, lines 1240-1254](https://github.com/flutter/flutter/blob/5048996dd0d3868fe53616c704c94d97a497acbb/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterEngine.mm#L1240-L1254), [FlutterViewController.mm, lines 458-526](https://github.com/flutter/flutter/blob/5048996dd0d3868fe53616c704c94d97a497acbb/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterViewController.mm#L458-L526)). An ordinary client read of `accessibilityChildren`/AX attributes is **not** an enablement path in these inspected files. A scan of the 105 current macOS framework `.mm/.m/.h/.cc/.swift` files found no `AXManualAccessibility` reference and found `AXEnhancedUserInterface` only as that notification key, not as a setter. This does not prove how Rive's bundled Flutter version or the earlier CUA session changed exposure; it does rule out treating a generic AX read or either AX setter as a documented Flutter activation contract.

A current read-only CUA AX view of the running Rive app did show populated semantics: one Rive window contained distinct unnamed subtrees with hierarchy content, animation-list content, stage controls, inspector controls, and a focused editable field. This establishes that panel *content* can be differentiated in that state. The animation list is not evidence of the Animate-mode timeline itself. The representation did not show an explicitly named panel ancestor for those subtrees, and it omitted raw AX identifiers and geometry, so neither absent panel identifiers nor reliable focus-to-panel mapping can be concluded. No pointer/focus transition was made in that observation; the earlier shallow `AXGroup` state and current populated state still need a controlled cause/consistency probe.

A later read-only view showed that the root group's multiline label mixes built-in tabs with private document metadata, while its panel-like child containers are unnamed. The Stage subtree exposes exact built-in `Stage` text and a percentage zoom readout. The inspector subtree exposes built-in section text such as `Computed Transform`, `Constraints`, and `Draw Order`. Hierarchy rows and animation rows include user-authored names. A root-level `Hierarchy` or `Animations` token therefore cannot be assigned to a sibling panel, and arbitrary row text must never become a panel signature. The probe below splits multiline AX text locally, keeps only exact allowlisted chrome tokens (or a boolean zoom-readout token), and discards original strings and numeric percentages immediately. These observations still do not establish hit-test geometry or live focus transitions.

Build24's live, read-only collector result narrowed the problem: all eight numeric-field captures contained only `AXWindow → AXTextField`, with no chrome anchors. The native editing control is detached from Flutter's semantic panel siblings, so following its parent chain alone cannot identify the inspector. This is evidence about that field and build, not proof that other panels behave the same way. The collector candidate now discovers a shallow window/Flutter/root tree, then inspects only semantic sibling groups whose AX bounds contain the focused or hit control. It requires local panel-specific anchors; the mixed root label cannot supply a sibling's identity.

Build26's saved diagnostic showed why the first sibling scan still stopped early: after the detached field, it found three successive full-window `AXGroup` wrappers with no anchors, with the deepest at absolute depth 3. Discovery stopped at that depth, before reading its pane children; the 10-node result was a traversal limit, not evidence that pane semantics were absent. The revised scan follows only groups whose bounds cover at least 80% of the focused window, through absolute depth 6. It does not expand small controls or pane contents during discovery. A later bounded local scan still requires a pane's own geometry and chrome before classification. The 80% threshold is a wrapper filter, not a hard-coded panel rectangle.

Rive describes the hierarchy as an object tree and the timeline as an Animate-mode editing surface ([hierarchy](https://rive.app/docs/editor/interface-overview/hierarchy), [timeline](https://rive.app/docs/editor/animate-mode/timeline)). These editor concepts may overlap in one window; selecting an object in the hierarchy may update the timeline and inspector without moving keyboard focus. Rive's published desktop MCP page describes scene queries and edits, but gives feature categories rather than an exhaustive named tool catalog; it does not claim an active panel or focus event API ([Rive MCP](https://rive.app/docs/editor/ai/mcp)). The current callable Rive MCP catalog exposes read-only `session_info` (active file/tab), `get_selection` (selected scene-object IDs/names/types/parents), `list_artboards` (including a sticky `isActive` and a selection artboard ID), and `open_file_editor` read commands for file/artboard state. A read-only `session_info` response confirmed file/tab fields but no panel/focus field. Selected scene object, active file tab, and artboard are **different state** from the panel receiving keyboard input; none of these observed tools is a direct active-panel feed. This negative finding is limited to the exposed catalog and response inspected here, not a claim that Rive has no private or future API. File parsers, Luau scripts inside a Rive file, and runtime data-binding APIs likewise do not reveal which desktop editor panel is accepting a K40 dial. A first-party, read-only editor-focus/active-surface API would be the strongest long-term option if Rive exposes or adds one. The web editor might permit DOM-based inspection where Flutter web accessibility is enabled, but Flutter web renders a canvas and builds a separate semantics layer; this would be a different integration and would not identify the installed desktop editor's panel ([Flutter web accessibility](https://docs.flutter.dev/ui/accessibility/web-accessibility)).

## Current KDCustom fit and MVP behavior

Today `FocusedInputObserver` polls focus every 250 ms, listens for focus-change notifications, and records only focused role, subrole, identifier, label, kind, bundle, and a token ([lines 210-236](../Native/Platform/FocusedInputObserver.swift), [393-418](../Native/Platform/FocusedInputObserver.swift), [452-507](../Native/Platform/FocusedInputObserver.swift)). It does **not** retain parent ancestry, geometry, hit-test results, a pointer event, window identity, or a panel ID. `FocusSnapshot` and `FocusRule` have no panel field; ordered rules match focused metadata only ([Models.swift](../Native/Core/Models.swift)). On each dial event, `StudioModel` expires old focus and resolves a binding; the matching rule supplies only four dial bindings while buttons remain in the selected group ([StudioModel.swift](../Native/App/StudioModel.swift), [Models.swift](../Native/Core/Models.swift)). Its output gate already responds to foreground, secure input, permissions, pause, device/session state, and app identity. Preserve those boundaries.

Proposed classifier state: `{app PID, AX window identity, focus token, focus metadata/ancestry, last physical click target/point/time, resolved panel, confidence, generation}`. Make the resolution order explicit:

1. A *currently verified* readable numeric text control wins only while it is still the focused Rive element and no later Rive pointer interaction has invalidated that numeric lease. Preserve the existing pre-write focus/value checks. A click into timeline/hierarchy/canvas must revoke numeric routing immediately, even if Rive leaves the old text field in `AXFocusedUIElement`.
2. A labeled AX ancestor or click hit-test object that unambiguously identifies a panel may select that panel. Check the hit object's PID/window against the current frontmost Rive app and the click's window; ignore menus, dialogs, popovers, overlays, and ambiguous roots. Recheck focus after the click settles. A click location classifies **last interaction**, not keyboard focus.
3. If AX remains generic, use per-window-relative regions only after user calibration and only while the same panel layout/window remains valid. Revoke on resize, display change, full screen change, editor mode change, panel rearrangement, app switch, or unrecognized overlay. Avoid a universal hard-coded Rive rectangle.
4. If evidence conflicts or is missing, use the profile's default dial bindings or an explicit manually selected group. Never infer numeric editing from a stale value, pointer hover, selection, or the previous panel alone. A keyboard shortcut that moves focus without a click needs fresh AX evidence; otherwise resolution is unknown.

The same classifier should emit a single generation-stamped route decision consumed at dial input, so a pending action is cancelled whenever its panel, window, focus, or app generation changes. Add panel-aware rules to the validated configuration service only after probes establish stable identifiers; keep existing focus-only rules and profiles compatible. Existing dial-only rule precedence and button behavior should remain intact. A small status label can show `Numeric field`, `Timeline`, `Hierarchy`, `Canvas`, or `Default/unknown` with the evidence source, so a user can see and correct routing before turning a dial.

### Isolated candidate now in source

`Native/Platform/RivePanelProbe.swift` adds `collect(rivePID:pointer:)`, an **on-demand** read-only sampler to call from a serial background AX worker after a focus/click transition or deliberate diagnostic request. It checks the foreground Rive PID, focused AX window, and optional click's PID/window; it rechecks PID/window before returning. It caps traversal at 160 nodes, absolute depth 8, 48 discovery nodes with wrapper traversal no deeper than 6, a 400 ms overall deadline, and 40 ms or less per AX message. An individual remote AX call may overrun the overall deadline by its remaining messaging timeout, after which the result is discarded. The sampler walks the focused/hit paths, discovers window-sized wrappers and sibling pane bounds, then inspects only local groups containing the target geometry; it does not traverse the entire Rive document tree every 250 ms. Unsupported AX attributes/geometry, shallow trees, budget exhaustion, app/window changes, and stale clicks fail closed. It reads AX `Value` only for static text, never editable fields. Its snapshot contains sanitized roles, allowlisted built-in tokens, frames, node ancestry, freshness, and scope—no raw text, values, filenames, or scene names.

`Native/Core/RivePanelClassifier.swift` is a pure function over that snapshot. It offers separate `focusedPanel`, `lastInteractedPanel`, and `automaticPanel` with confidence/reason; a containing semantic sibling is marked as geometry evidence. `automaticPanel` requires a bounded local container with panel-specific chrome plus structure: Stage and zoom readout for canvas; two inspector anchors; Timeline and temporal chrome; or a Hierarchy button and outline-like structure. The current live AX view has **not** proven the latter two signatures. Combined root labels, generic groups, missing geometry, overlapping independent panes, popovers/menus/dialogs/sheets, secure focus, stale pointer events, incomplete scans, and focus/click disagreement return unknown. A click-only panel candidate is diagnostic and cannot automatically route dials. Numeric focus remains the existing focused-input worker's responsibility. These new files are not wired into configuration or device output.

## Bounded, read-only diagnostic (next live evidence)

Run only when the editor is available for a deliberate test. Record sanitized roles, allowlisted chrome tokens, bounds, parent-node relationships, API status, timestamp, PID/window key, and focus/hit identity—never field contents, selected object names, document text, raw labels, or screenshots. Use one unchanged Rive document, one editor window, and each relevant mode. For each **numeric field**, **timeline empty/ruler/key area**, **hierarchy row/blank area**, and **canvas empty/object area**, perform a click and a keyboard-navigation transition, then compare the on-demand focused path, hit path, and bounded local subtrees. Note whether Rive's accessibility tree is shallow or populated before and after the first accessibility client attaches; do not set undocumented accessibility attributes in this pass. Repeat after Enter in a numeric field, after leaving it by clicking each panel, after mode switch, resize, window switch, and app switch. Compare results across a second launch/version only if the first pass suggests stable signatures.

Accept an automatic route only if repeated transitions identify the intended panel without false switches and the dial consumes the latest generation. Specifically test `numeric → timeline` and `numeric → hierarchy` with stale numeric AX focus, timeline clicks beside keys and in blank space, hierarchy selection that changes the inspector/timeline, canvas drag, popover/menu, keyboard-only movement, window resize, and Rive losing foreground. **Zero numeric actions after leaving the numeric field** is a hard requirement. Unknown/ambiguous observations must resolve to defaults; no panel-specific action should execute under a mismatched app/window or after a revoked focus lease. Record false switches separately from missed switches. A successful numeric detent does not close these panel cases.

If AX metadata is stable, implement AX ancestry/hit-test first. If it is generic but panel geometry is stable, test click-aware calibrated regions. If both fail, retain explicit manual group selection and consider opt-in Vision only for layout recognition. ScreenCaptureKit capture requires user-granted Screen Recording permission, and Vision OCR recognizes text from images; neither provides authoritative focus, so capture should be window-scoped, on-device, event-driven, and disabled by default ([Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit), [Apple Vision](https://developer.apple.com/documentation/vision/recognizing-text-in-images)).

## Evidence limit

This note uses source inspection, the installed app's `Info.plist` (`app.rive.editor`) and presence of `FlutterMacOS.framework`, official API/editor docs, the reported numeric-field live test, a read-only Rive AX view, and a read-only Rive MCP `session_info` response. It did not edit a Rive file, test AX panel transitions, or call a selection tool. Upstream Flutter source may not exactly match Rive's bundled build. Thus the panel classifier is a proposed MVP and the detection ranking is conditional on the diagnostic above.

The pure fixtures in `Tests/RivePanelClassifierTests.swift` pass with the direct Command Line Tools compiler (`swiftc -warnings-as-errors`), and the collector/core files pass a joint typecheck. No installed-app AX call, real panel transition, device action, or end-to-end routing test was performed for this candidate.

## App integration

The diagnostic session is now integrated in the candidate build through `RivePanelDiagnostics`: an explicit two-minute arm, AX capture after Rive activation or physical clicks, bounded in-memory structural snapshots and a chronology of device/output/focus events. The Intelligent dials sheet and `kdcustom_get_focused_input` expose start/stop and historical results. No classifier candidate changes runtime routing. Live panel transitions and false-switch acceptance remain pending.
