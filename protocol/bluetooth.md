# K40 Bluetooth path: driver inspection and live validation

Read-only inspection of the installed ARM64 `HuionDriver` binary, checked against live GATT captures in `evidence/capture-2026-09-23T00-13-53Z/events.jsonl` and `evidence/capture-2026-09-23T00-16-21Z/events.jsonl`. Addresses below identify driver methods. The completed input and display observations are counted in [bluetooth-results.md](bluetooth-results.md).

## GATT discovery

`BlueDevFinder::ScanBLE` (`0x10004e32c`) retrieves connected peripherals advertising service `FFE0`; `centralManager:didConnectPeripheral:` (`0x10004e4c8`) calls `discoverServices:` for `FFE0`. `BluConnectObj::peripheral:didDiscoverServices:` (`0x10004d7ac`) asks for characteristics `FFE1` and `FFE2`. `didDiscoverCharacteristicsForService` (`0x10004d914`) stores both and calls `setNotifyValue:YES` on each. It signals its connection callback once both characteristics and its finder callback are present; it does not wait in this method for a notification-state confirmation.

`FFE2` is the driver's write characteristic **and command-response notification source**. `FFE1` supplies the pen/raw-input notifications. `ZBltObj::ConnectBluetooth` (`0x10004f668`) passes the callback pair `[CallBack_ReceiveBleCommandData, CallBack_ReceiveBlePenData]`; `BlueDevFinder::SetDataHandle` (`0x10004e86c`) copies them into the `BluConnectObj` callback slots at offsets `0x28` and `0x30`. `peripheral:didUpdateValueForCharacteristic:` (`0x10004dc10`) dispatches `FFE2` to slot `0x28` and `FFE1` to slot `0x30`. The live FFE2 C9 reply below confirms the command-response assignment. The macOS Bluetooth HID descriptor observed for `Keydial Remote-365` exposes standard keyboard/consumer/mouse reports only; this GATT path indicates why HID report capture alone may miss vendor controls.

## Identity and mode sequence

`ZDevMng::OnBleDevMatching` (`0x100051f50`) first connects by peripheral UUID, calls `ZBltObj::GetTabletInfoEx` (`0x10004fc8c`), checks the resulting RD code against `T221` and validates the customer code, then calls `ZBltObj::GetTabletInfo` (`0x10004fb98`). `GetTabletInfoEx` calls `RequestInfo(0xC9)`, followed by `GetTabletInfo` calling `RequestInfo(0xC8)`. This mirrors the USB detector's C9 then C8 order. Both replies were captured live over BLE.

`ZBltObj::RequestInfo` (`0x10004f764`) calls `SendCmd(index)`, then waits in a Qt event loop with a 5000 ms timeout for a command response. `BluConnectObj::GetStringDesc` (`0x10004d6b0`), reached through `SendCmd`, constructs an eight-byte write `CD <index> 00 00 00 00 00 00` to `FFE2`. `FFE2` notifications feed `ZBltObj::CallBack_ReceiveBleCommandData` (`0x10004f4a4`): it uses notification byte 1 as a command index and stores the whole notification under that key. The callback quits the active wait loop on any FFE2 command notification; matching the requested index occurs only afterward. `CBluToothDataBuffer::AddData` (`0x100071bcc`) replaces a previous value for the same index; it does not concatenate notification fragments. `RequestInfo` looks up the requested index after the wait and copies at most the caller's buffer size, preserving bytes 0 and 1. It does not clear the keyed buffer before sending or remove the stored value after reading. Consequently, a separate implementation should associate responses with the current request and retain each raw frame and its length, instead of treating a stale keyed value or a short ACK as a fresh descriptor.

In this path, `didUpdateValueForCharacteristic` requests 20 bytes from each notification value. `GetTabletInfoEx` requires more than 18 returned bytes for C9 and parses identity text from offset 2; `GetTabletInfo` requires at least 18 bytes for C8 and parses fields from offset 2. Neither validates a USB string-descriptor header. The live BLE C8 reply begins `14 c8`, unlike the USB C8 fixture's `14 03`; a BLE implementation must use the BLE response framing.

At 00:14:44 UTC, the standalone POC wrote `cd c9 00 00 00 00 00 00` to `FFE2` (write type 1) and received an **FFE2** notification `13 c9 48 55 49 4f 4e 5f 54 32 32 31 5f 32 35 30 38 30 31`. Its first byte is length `0x13` (19), second byte matches command index `0xC9`, and bytes 2 onward spell `HUION_T221_250801` in ASCII. The POC was listening for C9 on FFE1 and therefore timed out despite this response. The raw event and timeout are in `evidence/capture-2026-09-23T00-13-53Z/events.jsonl`.

The corrected POC subsequently sent C9 then C8 on `FFE2` and received replies there: C9 `13 c9 48 55 49 4f 4e 5f 54 32 32 31 5f 32 35 30 38 30 31`; C8 `14 c8 01 00 00 01 00 00 00 00 00 00 00 0e 00 80 40 00 32 10`. Its status then reported Bluetooth controls enabled. These are observed bytes, not a complete interpretation of the C8 fields.

## Input and screen writes

`FFE1` notifications feed `ZBltObj::CallBack_ReceiveBlePenData` (`0x10004f4e8`) and its read queue. In `ZTabletConnectObj::ReadData` (`0x100061f80`), the BLE branch accepts a queued notification only when the read succeeded and length exceeds 13 bytes. It copies 12 bytes beginning at notification offset 1; if copied byte 1 is `0xD1`, it skips the packet. Otherwise it forces copied byte 0 to report ID `0x08` and presents the 12-byte frame to the existing K40 parser. Live raw `FFE1` notifications were 14 bytes; for example `55 54 e0 01 01 02 00 00 00 00 00 00 00 e4` normalizes to `08 e0 01 01 02 00 00 00 00 00 00 00`, matching that static path. The last byte's meaning has not been established.

`ZTabletConnectObj::K40_SetGroupName` (`0x100063238`) and `K40_SetEKeyName` (`0x1000633b0`) call `ZBltObj::SendData` with the same 64-byte label packet used by the USB path when BLE is open. `BluConnectObj::SendData` (`0x10004d754`) creates one `NSData` of the supplied length and writes it to `FFE2`; no packet segmentation appears in that method. Both command and label writes derive CoreBluetooth's write type from the characteristic's `0x04` WriteWithoutResponse property: type `1` (without response) when set, otherwise type `0` (with response). A successful call into this path alone would not prove display acceptance; physical screen confirmation is needed.

The installed driver sends BLE command `0xCD` when `ZBltObj::CloseBLE` (`0x10004f2b4`) is called while its open flag is set. The exact device-side effect is unverified. Live testing confirmed all eight temporary BT labels on the physical screen and raw input from eight keys, both group switches, and both dial directions. Reconnect and six-group profile persistence have not been tested in this BLE capture.
